# 게이트 5 — 다중브랙 시뮬레이션 검증 (합성 지형 + 야디지 실측 그린)

> 이 문서는 전체 구현 프롬프트(`multibreak_putting_implementation_prompt.md`) 6장 "게이트 5 — 합성 다중브랙 검증"의 상세 확장판입니다. 원본 6장의 목적(지형이 주어졌을 때 홀인 후보 탐색 → 선정 로직 → 궤적 시각화가 정상 동작하는지 확인)은 그대로이되, 지형 소스를 3종으로 구성합니다. 게이트 1~4는 완료·합격 상태를 전제합니다.

## 0. 이번 게이트에서 새로 들어오는 것 — 야디지코리아 실측 그린 데이터

프로젝트 담당자가 야디지코리아로부터 전국 골프장 그린의 항공측량 데이터(20cm 격자, 절대표고)를 구매했습니다. 이 데이터를 그린별 압축 바이너리 높이맵(`.grnh.gz`)으로 변환하는 Python 파이프라인(`yardage_converter.py`)이 이미 만들어져 있고, 샘플 골프장 1개(36개 그린)로 실행 검증까지 마쳤습니다. 이번 게이트에서는 이 실측 데이터를 `TerrainField`의 세 번째 지형 소스로 통합합니다.

**중요한 전제 조건 두 가지**:
1. 이 데이터는 **정적(static)** 지형입니다 — 실전에서는 게이트 1~4의 라이다 실시간 스캔을 계속 사용하며, 이 데이터는 **다중브랙 알고리즘 검증 + 앱 내 시뮬레이션(가상 연습) 모드** 용도로만 씁니다. 라이다 통합 경로를 대체하지 않습니다.
2. 원본 CSV가 준 사각좌표는 위경도(EPSG:4326)이고, XYZ는 한국 UTM-K(EPSG:5179)입니다. 변환 파이프라인이 이미 두 좌표계를 정합했으므로, Swift 쪽에서는 `.grnh` 파일 안의 로컬 평면좌표만 다루면 되고 위경도 변환을 다시 할 필요는 없습니다.

## 1. `.grnh` 바이너리 포맷 명세 (Swift 파서 작성용)

파일은 gzip으로 압축되어 있습니다. 압축 해제 후 구조 (little-endian, 패딩 없음):

| 오프셋 | 크기 | 타입 | 필드 | 설명 |
|---|---|---|---|---|
| 0 | 4 | bytes | magic | `"GRNH"` (ASCII) |
| 4 | 2 | UInt16 | version | 현재 `1` |
| 6 | 8 | Double | originX | 격자 (col=0) 셀의 로컬 평면 X좌표(m), EPSG:5179 |
| 14 | 8 | Double | originY | 격자 (row=0) 셀의 로컬 평면 Y좌표(m), EPSG:5179 |
| 22 | 4 | Float | cellSize | 격자 간격(m), 통상 0.2 |
| 26 | 4 | Float | zOrigin | z 기준값(m) |
| 30 | 4 | UInt32 | nx | 가로 셀 수 |
| 34 | 4 | UInt32 | ny | 세로 셀 수 |
| 38 | nx×ny×2 | Int16[] | cells | row-major (row 인덱스 = Y 증가 방향), 결측 셀은 `-32768` |

**높이 복원식**: `height(col, row) = zOrigin + cells[row][col] / 1000.0` (미터), `cells[row][col] == -32768`이면 결측.

**좌표 복원식**: `worldX(col) = originX + col * cellSize`, `worldY(row) = originY + row * cellSize`. 이 world 좌표는 EPSG:5179 평면좌표이지, 게이트 1~4에서 쓰던 "볼→홀 방향=+Y" 로컬 좌표계가 아닙니다 — **아래 2절의 정렬 절차가 필요합니다.**

Swift 파서 구현 시 참고: `Data(contentsOf:)`로 읽은 뒤 gzip 압축 해제(예: `Compression` 프레임워크의 zlib 알고리즘, 또는 검증된 오픈소스 gzip 라이브러리), 이후 위 오프셋대로 `withUnsafeBytes`로 각 필드를 파싱합니다.

## 2. 로컬 좌표계 정렬 — 볼·홀 위치를 어떻게 정하나

실제 라이다 스캔에서는 볼→홀 도보 방향이 자연스럽게 +Y가 됩니다. 야디지 데이터에는 볼/홀 위치가 없으므로(그린 전체 지형만 있음), 시뮬레이션에서는 다음 규칙으로 정합니다:

1. `.grnh` 격자에서 **결측 아님(유효) 셀들의 중심**을 그린 중심으로 삼는다.
2. 시뮬레이션 시나리오마다 볼 위치·홀 위치를 그린 유효 영역 내에서 지정한다(테스트 케이스별로 지정 — 3.2절 참고).
3. 볼→홀 벡터를 +Y로 하는 회전변환을 EPSG:5179 평면좌표 기준으로 1회 계산해, `.grnh`의 전체 셀을 게이트 1~4와 동일한 로컬 좌표계로 재투영한다. **이 재투영·리샘플링 로직은 게이트 1의 5.1절 "좌표계 통합" 절차와 동일한 종류의 작업이므로, 이미 구현된 코드가 있다면 재사용한다.**
4. 재투영 후에는 설계문서 v2 5.2절의 파이프라인(스무딩 → 기울기 필드 사전계산)을 **그대로** 적용한다. 야디지 데이터는 20cm 격자라 라이다보다 성기지만, 스무딩·기울기필드보간 로직 자체는 격자 간격에 무관하게 동작해야 하므로 코드 분기 없이 재사용 가능해야 한다.

## 3. 지형 소스 3종

### 3.1 (a)(b) 합성 지형 — 원안 그대로

- (a) 사인파 능선형 이중브레이크
- (b) 대각 안장(saddle)형

이 둘은 프롬프트 원문 6장 그대로 구현한다. 극단적 케이스에서 선정 로직이 깨지지 않는지 보는 스트레스 테스트 용도이므로 유지한다.

### 3.2 (c) 야디지 실측 그린 — 원안의 "인공 지형과 실측 혼합" 대신 실제 그린 그대로 사용

원래 계획은 "게이트 1 실측 높이맵에 인공 브레이크를 더한 하이브리드"였으나, 이제 노이즈 없는 정밀 실측 그린 전체를 쓸 수 있으므로 **인공 브레이크를 얹지 않고 그대로 사용**한다.

**번들 리소스: 골프장 1개소(`128_001`)의 36개 그린 전체**를 사용한다(`samples_all36/` 폴더, 총 696KB — 용량 부담이 없으므로 일부만 추리지 않고 전부 포함). 표고차는 `manifest.json`의 `relief_m` 필드 기준 0.585m(가장 완만)~2.457m(가장 심한 다중브랙)까지 자연스럽게 분산되어 있어 별도 선별 없이도 다양한 케이스를 커버한다.

각 그린에 대해: 유효 셀 영역 내에서 볼 위치 1곳(그린 가장자리 근처), 홀 위치 2~3곳(그린 내 다른 지점들)을 지정해 여러 볼-홀 조합으로 테스트한다. 36개 중 표고차가 가장 완만한 그린들은 홀인 후보가 0개로 나올 수 있는데, 이 경우 프롬프트 5.6절의 3순위(캡처 반경 50cm 완화 재계산)가 정상 동작하는지 확인하는 유용한 케이스이니 오류로 취급하지 않는다.

> 참고: 이번 게이트는 알고리즘 검증이 목적이라 1개 골프장(36개 그린)이면 충분하다. 전국 데이터를 전부 변환해 앱의 "시뮬레이션(가상 연습) 모드" 콘텐츠로 쓰는 건 별도 제품 결정 사항이며, 게이트 5 진행의 선행조건이 아니다.

## 4. 구현 내용

1. **`.grnh` 파서** (`GreenHeightmapLoader.swift`): 1절 명세대로 파싱, 결측 셀 마스크 유지.
2. **좌표 정렬 모듈** (`GreenAligner.swift`): 2절 절차. 입력(볼 EPSG:5179 좌표, 홀 EPSG:5179 좌표) → 회전변환 파라미터 → 재투영된 로컬 격자.
3. **`TerrainField` 확장**: 기존 게이트 4의 합성 이중평면 생성자에 더해, `.grnh` 기반 생성자를 추가한다. 내부적으로 스무딩 → 기울기 필드 사전계산은 기존 파이프라인(설계문서 5.2절 구현체)을 그대로 호출한다 — **분기 없이 재사용되는지가 이번 게이트의 숨은 체크포인트다.**
4. **선정 로직**: 프롬프트 원문 5장 그대로(`scanInitialConditions` → 오버런 시뮬레이션으로 정지점 산출 → 홀 중심+X 최근접 후보를 1순위, `ballSpeedForHole` 최소를 2순위, 후보 0개 시 반경 50cm 완화 재계산). X는 설정 가능한 파라미터, 기본값 0.35m(설계문서 v2 5.6절).
5. **시각화**: 기존 `TrajectoryOverlayRenderer`(게이트 4에서 구현됨)를 재사용해, 지형별로 1·2순위 궤적을 높이맵 히트맵 위에 오버레이한 PNG를 출력한다.
6. **번들 자산**: 위 5개 그린의 `.grnh.gz` 파일을 앱(또는 테스트 타깃) 리소스로 추가한다. 전체 크기는 100KB 미만이라 부담 없다.

## 5. C¹ 연속성 스팟체크 (게이트 4에서 이월된 항목)

게이트 4의 이중평면 테스트는 평면 경계의 "의도된 불연속"만 확인했고, **매끄러운 단일 곡면 내부에서 기울기 보간이 셀 경계마다 끊기지 않는지**는 아직 검증되지 않았습니다. 이번 게이트에서 다음을 추가합니다:

- 야디지 실측 그린 1개(예: `128_001_1_01_3`)를 대상으로, 격자 셀 경계를 걸치는 인접한 두 점(예: (i,j)와 (i+0.01,j))에서 `TerrainField.gradient(at:)`를 조회해, 두 값의 차이가 격자 간격 대비 비정상적으로 크지 않은지(연속적으로 변하는지) 확인하는 단위테스트를 추가한다. 셀 경계를 여러 곳(최소 10곳) 샘플링해 불연속 스파이크가 없는지 확인.

## 6. 합격 기준

- (a)(b)(c) 세 지형 소스 모두에서 홀인 후보 탐색 → 선정 로직 → 시각화가 정상 동작
- (c)의 5개 실측 그린 중 최소 1개에서 홀인 후보가 0개로 나오는 케이스가 재현되고, 3순위(반경 완화) 로직이 정상 동작함을 확인
- 브레이크 방향과 궤적 휨 방향의 물리적 정합(내리막 쪽으로 휘는지)을 5개 실측 그린 각각에서 시각적으로 확인
- X(오버런 목표거리)를 0.108/0.35/0.43m로 바꿨을 때 최소 2개 그린에서 1순위 후보가 달라지는지 비교표 제출
- 5절의 C¹ 연속성 스팟체크 통과(10곳 샘플링, 불연속 스파이크 없음)
- `.grnh` 파서가 정상 동작함을 파이썬 변환기 출력(예: `128_001_1_01_3`의 nx=138, ny=133, 결측 0%)과 대조해 확인
- 전체 테스트 통과, 기존 앱 Release 빌드 성공

## 7. 시작 지시

1. `.grnh` 파서부터 구현하고, 첨부된 샘플 파일 하나(`128_001_1_01_3.grnh.gz`)를 로드해 1절 명세의 예상값(nx=138, ny=133, 결측 0%)과 일치하는지 먼저 확인한다.
2. 파서가 검증되면 좌표 정렬 모듈 → `TerrainField` 확장 순으로 진행한다.
3. (a)(b) 합성 지형은 기존 게이트 4 구현을 재사용하되 게이트 5 선정 로직과 연결한다.
4. 5개 실측 그린 전부에서 결과가 나오면 작업을 멈추고 6장 합격 기준을 항목별로 보고한다.
