# 스캔·LiDAR·경기 모드 대화 정리 (2026-08-13)

**문서 성격:** 코드 변경 이력이 아닌, 2026-08-13 세션에서 논의된 **설계·현장·하드웨어 맥락** 정리.  
**배경:** 실외 필드 테스트 약 30회 중 **10m 롱 퍼팅 2회** 홀인 경로 미발견.

---

## 1. 출발점: 필드 테스트 결과

약 **30회** 다양한 조건(5m·10m, 트위스트·업/다운·좌/우 편경사 등)에서 **홀인 경로를 못 찾은 경우 2회** — 둘 다 **10m 롱** 퍼팅.

| 항목 | 결론 |
|------|------|
| 격자 90×90 | 실패 원인 아님 |
| 그린스피드 2.5m | 실패 원인 아님 |
| 의심 원인 | 복도 폭, 트위스트 flank 스캔, 홀 뒤 언듈레이션, LiDAR 시야 편향 |

---

## 2. 복도(코리도) 폭

**「넓혀」** → lateral **±1.25m → ±1.75m** (전체 폭 3.5m)

- 10m + 트위스트/편경사에서 **높은 쪽이 복도 밖**이면 크로스폴이 높이맵에 안 들어가 경사가 평평하게 잡힐 수 있음.
- 2/30만 실패 → **폭만 키운다고 100% 해결은 아님**, 다만 10m 롱·편경사에는 **우선 튜닝 후보**로 적합.

등고선/흰 메시 표시는 **±3m**로 맞추자는 요청.

---

## 3. LiDAR·카메라 하드웨어 특성

### 3.1 광학 줌 없음

- LiDAR는 RGB처럼 **0.5x·1x 줌 없음** — FOV 고정.
- 「광폭 스캔」은 줌이 아니라 **스캔 동선·기울기** 문제.

### 3.2 센서 위치 — 좌측 상단 치우침

- iPhone Pro 뒷면(세로) 기준 **LiDAR·카메라가 중앙보다 왼쪽(좌측 상단)** 에 몰려 있음.
- Apple은 정확한 오프셋·FOV를 공식 미공개.

| 손잡이 | 기하학적 효과 |
|--------|----------------|
| **오른손** | 그립이 폰 오른쪽 → LiDAR는 **몸/바깥쪽**으로 치우치기 쉬움 → **퍼트 라인 위 depth가 상대적으로 적게** 쌓일 수 있음 |
| **왼손** | 반대로 **라인 쪽을 더 넓게** 훑을 수 있음 |

→ **「오른손 스캔 → 홀인 후보·경로 다양성이 왼손보다 적을 가능성」** 이라는 가설에 **동의**.

**코드는 좌우 대칭(±corridor)이지만, 실제 depth 수집 기하학은 대칭이 아님.**

### 3.3 FOV (검색·논의)

- Järvenpää 등 추정 **약 61°×48°** (H×V).
- **1.2m 높이**에서 바닥 커버: 대략 **한 프레임 ~1.4m 폭** 수준.
- **복도 3.5m 전체가 한 번에 다 들어오지는 않음.**
- 「60°면 바닥이 넓게 스캔되지 않나?」→ **pitch(아래 기울기)** 에 따라 실제 바닥 폭은 **1~2m대**로 제한됨.

### 3.4 스캔 자세 팁 (대화 결론)

| 구간 | 권장 |
|------|------|
| 볼·홀 지정 | 화면 **중앙 십자선** |
| 걸으며 스캔 | 볼·홀이 항상 정중앙일 필요는 없음 — **퍼트 라인이 LiDAR(폰 왼쪽) 쪽**에 오게 기울이기 |
| 오른손 | 화면 **중앙~약간 오른쪽**에 라인을 두는 식 |
| flank | **양쪽 flank**에서 조금씩 지나가기 — 한쪽만 보면 grazing angle 편향 |
| 홀 주위 | **크게 돌 필요 없음** — 복도(±1.75m) 안에서 **라인 위·옆**을 걸으며 양쪽에서 보는 것이 핵심 |

## 4. 왼손+왼쪽 돌기 vs 오른손+오른쪽

**「왼손·홀 왼쪽 돌기가 더 정확한 것 같다」**

| 관점 | 내용 |
|------|------|
| 코드 | 볼→홀 좌표·복도는 **좌우 대칭** — 알고리즘이 왼쪽을 prefer하지 않음 |
| 실제 depth | LiDAR 오프셋 + 손잡이 + 걸음 flank → **비대칭** |
| grazing angle | flank마다 depth 품질 상이 |
| TemporalSurfaceFusion | **서로 다른 시점 2곳 이상** 선호 → 한쪽 flank만 약하면 그쪽 경사·β가 틀어짐 |
| 트위스트·편경사 | **브레이크 하이사이드를 더 잘 본 쪽** 스캔이 맞게 느껴질 수 있음 |
| 왕복 | **같은 손 유지**가 손 바꾸기(그 순간 흔들림)보다 낫다는 의견 |
| 드리프트 | 왕복이면 볼 재지정 없이 복귀 후 종료 — **드리프트 보정** 포함 |

---

## 5. 홀 뒤·볼 뒤 지형

### 5.1 홀 뒤 ~1m

**「홀 뒤 1m 언듈레이션이 홀인에 중요한데 쓰이나?」**

- **높이맵 복도**에 홀 뒤가 들어가야 홀 근처·통과 구간 경사가 맞음.
- LiDAR FOV로 **추가로 1m 더 걸어가지 않아도** 홀 뒤 ~1m는 **시야로 스캔 가능**.
- → 경기 모드에도 **높이맵에 포함**하기로 (초기에는 타인 라인 회피로 0m였으나 변경).

### 5.2 볼 뒤 0.5m

**「볼 뒤 경사도 쓰나?」**

- `ballEndMargin`은 **볼 뒤(스탠스 쪽) 0.5m** — UI 「볼 앞」은 **오표기**.
- **직접** 0.5m 뒤 지점을 샘플링하진 않음.
- 볼 위치 ∇H는 **주변 5cm 격자 + 스무딩 ~25cm** 로 계산 → 볼 뒤 데이터는 **간접적으로** 경사 안정화.
- 홀 뒤 1m만큼 **홀인·통과 판정**에 직접 중요하지는 않음.

## 6. 경기 중 0후보 문제 → 5단계 폴백

**「실제 경기에서 재스캔 불가 → 무조건 후보 1개는 나와야 한다」**

| 단계 | 이름 | 설명 |
|------|------|------|
| 1 | verified | 5.4cm 캡처 |
| 2 | relaxedCapture | 50cm |
| 3 | expandedSearch | v·β 확대 + 완화 캡처 |
| 4 | proximityEstimate | 홀인 미검증, lateral miss 최소 (UI 주황 경고) |
| 5 | flatHeuristic | β=0, 거리 추정 (UI 주황 경고) |

### 논의만 한 아이디어

- **proximityEstimate + 홀컵 5배(≈27cm):** 50cm 완화까지 실패 **후**라 **비효율**.
- **concedeCapture (~27cm):** 논의만, **미구현**.
- **볼 근처 가중치** (트위스트): 스캔 품질을 폰 세우기 등으로 **균일하게** 맞추고 있다면 **비추**.

## 7. 경기 모드 / 튜닝 모드

| | 경기 (Competition) | 튜닝 (Tuning, 기본값) |
|---|---|---|
| 스캔 경로 | **편도** — 홀 지정 **직후 계산** | **왕복** — 드리프트 보정 |
| 홀 뒤 높이맵 | ~1.0m (LiDAR FOV) | ~1.0m |
| 볼 뒤 | 0.5m | 0.5m |
| lateral 복도 | ±1.75m | ±1.75m |
| 용도 | 실제 필드, 타인 라인 회피 | 알고리즘 검증 |

**편도만으로도 충분한가?**

- 한 프레임 ~1.4m + **양 flank / tilt** 가 더 중요.
- **홀 크게 돌 필요 없음** — LiDAR FOV·복도만으로 홀 뒤 ~1m 포함 가능.
